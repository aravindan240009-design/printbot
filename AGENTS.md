# Print Bot shared contract
You are a principal engineering team collectively acting as: product owner, Indian print-shop domain specialist, UX/accessibility lead, solution architect, Rust/Windows engineer, Python backend engineer, frontend engineer, DevSecOps lead, privacy/security engineer, print pipeline engineer, QA and release engineer. Build the production-grade **Print Bot** multi-tenant subscription-based SaaS, not a demo UI.

## Non-negotiable product facts

1. Platform owner/super-admin commercially sells the **same Windows installer (.exe/.msi)** to independent Xerox/printing shops. Copying installer is allowed; access requires authentic shop login, short-lived authorized device pairing, valid server-side subscription entitlement and revocable asymmetric device credentials. Shop ID, device ID and subscription ID are *identifiers*, never secrets. Prefer TPM-backed nonexportable device keys when possible; fallback appropriately and record assurance level.
2. **Exactly one all-inclusive subscription plan** for now (monthly or annual billing of the same plan). **No Starter/Pro/Business tiers, premium feature gates, paid per-printer tiers or per-page software commissions. UNLIMITED printers per subscribed shop.** Shop subscriptions, shop-owner customer printing receipts, and any third-party payment fees are distinct financial flows. Manage approved installation/device identities separately; do not invent a 1-PC limit as a substitute for printer limits. Super-admin may explicitly manage authorized device policy without tiering features.
3. Absolute **shop-to-shop tenant separation**: guest sessions, customer identities (if present), uploaded files, rendered PDFs, QR links, pricing versions, printing preferences, orders, printers, approved PCs, print jobs, queues, payments, bookings, analytics, logs and messages belong to precisely one `shop_id`. Customer at Shop A is not silently merged with customer at Shop B even with the same number/device. Scope every query and object key and test both read and write isolation. Server resolves `shop_id` from authenticated shop membership or shop-bound guest session, NEVER from an unchecked request body/query field. PostgreSQL RLS plus application-level checks, composite tenant foreign keys and negative tests; include explicit background-worker/agent/service account scoping. Super-admin admin access via audited elevated scopes, not blanket document browsing.
4. Each subscribed shop customizes its own logo/branding, QR links, local languages, supported formats/services, pricing in Indian paise, operating hours, print settings, compatible printer routing, paper types, cash/online payment choices, retention policy (within platform maximum), staff permissions, notifications, booking slots and exactly one of TWO selectable order modes: **FULL AUTOMATIC** (zero staff approval for eligible, verified-paid, compatible jobs) and **MANUAL APPROVAL** (staff must approve/reject every submitted job). Cash/unverified jobs never bypass the payment/approval policy. Shop can switch mode only through authorized audited action; the switch should not retroactively reinterpret already-accepted jobs.
5. Customers **scan shop-specific QR → mobile web (no app/no mandatory login) → upload → configure → server-based preview + accurate price → pay/confirm → track and collect**. UX: 3 principal screens; fast on inexpensive Android + iPhone, English/Tamil initially, Hindi support; accessible 44px touch targets, clear status and progressive disclosure. Large set of *applicable* controls available from phone, but show basics first.
6. Customer configuration per file and optional apply-to-all: arbitrary valid non-contiguous PDF page ranges (`1-3,5,8-`), single pages, odd/even, preview-thumbnail selection, copies, collation, B&W/grayscale/color, one-/two-sided, duplex long-/short-edge, paper sizes A3/A4/A5/Letter/Legal as compatible, landscape/portrait/auto, scaling, margins, 1/2/4/6/9/16 pages per sheet, optional booklet, photo crop/zoom/rotate/layout/passport/ID front-back, multi-file reorder/merge, quality/paper/finishing where the shop and driver support. A document's **logical pages**, rendered sides and physical sheets are different accounting quantities. Separate document print from physical scanner/copier Xerox. Implement supported formats through safe explicit converters; never promise literally arbitrary file types.
7. Include **timed Xerox** meanings as separate services: (a) schedule print dispatch for a future eligible time, (b) reserve ready-by/pickup slots, (c) book assisted *physical original* Xerox service at counter, (d) optional timed access to actual self-service copier ONLY after compatible hardware and safety validation. Avoid promising unattended physical copying without scanner/copier automation.
8. Cloud style: secure **modular monolith** API + isolated conversion workers + persistent queues/outbox + independent Rust Windows printing service. Rust/Tauri 2 + React desktop UI; Python/FastAPI cloud API; React/Vite/TypeScript mobile PWA; PostgreSQL, Valkey (open-source Redis-compatible alternative), Celery or other OSS queue, Python `pypdf`/`pypdfium2`/Pillow, isolated Gotenberg/LibreOffice after license audit, optional `pikepdf`/qpdf and Apache/BSD/MIT/MPL/LGPL components only after notices/obligations verified. For object storage use a self-hostable OSS S3-compatible service after validating license (e.g., SeaweedFS), local filesystem for dev; production may opt into a paid managed service explicitly. PDF.js for browser previews; Konva for optional interactive image editor. Prefer Caddy for HTTPS/reverse proxy; Podman/Linux containers for development and deployment. Native Windows printing path must be tested on real printers; do not assume spooler printing PDF directly always works. Use PDFium/render-to-driver or other verified compatible OSS rendering path; do not secretly add commercial SDKs. Validate licensed redistributable components.
9. Security: private storage, sandbox risky conversion with no network and bounded CPU/RAM/time, MIME/file magic, decompression-bomb protection, antivirus policy, malware scanning decisions, rate limits, presigned upload/download scoped by shop and owner, TLS, RLS, CSP/CSRF protection, HttpOnly cookie sessions, staff RBAC, MFA for super-admin, durable audit log, encryption at rest/in transit, short retention and cleanup of both cloud and agent temp files. No secrets/customer document content in telemetry. Signed software release/update plan; testing can be unsigned, but production signing typically has a nonzero external cost.
10. Order integrity: immutable versioned `PrintPlan` consumed by renderer, quote, routing and spool. Pricing is server-authoritative and locked at payment checkout; per-shop pricing versions. Never mark paid from browser callback alone. Never assume Windows spooler disappearance means physical paper delivered. On ambiguous submitted outcomes use `COMPLETION_UNKNOWN` and supervised reconciliation, **never automatic reprint**. Separate job events, financial ledger and provider webhook idempotency; support safe refund/cancel/reschedule policies. Paid orders stranded by subscription expiry must be allowed to resolve/refund safely.
11. The development environment must be **free/open-source-first**: VS Code OSS-compatible editor (e.g. VSCodium), Rust toolchain, Python, Node, PostgreSQL, Valkey, Podman, pytest, Playwright, Vitest, cargo test/clippy, OpenAPI generator, OWASP ZAP Community, Gitleaks, Semgrep OSS or comparable open tools, local email sandbox, mock UPI/payment flows. Do not REQUIRE proprietary AI APIs, GitHub paid CI, AWS, R2, Supabase managed, managed Sentry, Twilio/WhatsApp, paid PDF libraries or payment gateways in local development. External live settlement and Windows itself are labeled unavoidable optional exceptions. Never assert license status or compatibility without checking pinned sources; produce `OSS_LICENSE_AUDIT.md` and SBOM.
12. Source truth order: (i) latest user requirements above, (ii) existing `Print_Bot_Master_Product_Technical_Architecture_and_Development_Plan.docx` and Claude PDF supplied in repository, (iii) this prompt, (iv) verified current official documentation. If conflict, prioritize latest user facts, record ADR and avoid silent changes. The pending external competitor Deep Research is not verified input until the real report is supplied.

## Rules for EVERY phase

- Work directly in current repository, inspect first, don't overwrite functioning components. Use one monorepo (pnpm for TS workspace, Python uv/venv, Cargo workspaces). Do not start unrelated phases or fake successful integrations. No throwaway toy demos; keep architecture incremental, testable and runnable.
- At the beginning summarize existing code/state, dependencies and gaps. Then implement this phase fully, writing real source, migrations, tests, fixtures and minimal documentation. If blocked by printer hardware, payment credentials, code-signing certificate or external provider, build an isolated simulator and state the real-world test gate as **BLOCKED**, never passed. No fake metrics. Avoid storing real production secrets or user uploads in git.
- Dependency policy: Before adding a library, identify package/version/license and note legal obligations for commercial distribution. Prefer MIT/Apache-2/BSD, review MPL/LGPL, avoid AGPL/GPL/SSPL/RSAL/proprietary or unknown without explicit permission and legal signoff. Include open-source substitutes and document any unavoidable proprietary interface/fee. This is licensing guidance, not legal advice.
- Tests: unit, integration, E2E, cross-tenant negative tests, malformed file, authorization, idempotency, concurrency, network failures, browser/mobile accessibility where relevant. Log all execution commands and results; no fabricated passing screenshots.
- End each phase with: `IMPLEMENTED`, `TESTED`, `BLOCKED/UNVERIFIED`, exact changed files, architecture decisions (ADR), security/privacy checklist, runnable local commands, screenshots/visual QA where applicable, open risks, and a short copy-paste handoff summary for next phase. Do not claim phase completion when exit criteria remain blocked.
